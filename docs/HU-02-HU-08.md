# HU-02 / HU-08: contrato y alcance del incremento

Antes de programar se contrastaron backlog, decisiones, esquema SQL y columnas/
trigger del PostgreSQL activo, módulos, JWT/RBAC, consultas y pruebas existentes.
No se necesitan columnas nuevas ni se alteran claves, contraseñas o datos previos.

## Permisos y contratos implementados

- `GET /api/triage/panel`: solo MEDICO. Último triaje de cada paciente registrado
  en las últimas 24 horas, paginado (`page`, `limit`), ordenado I, II y revisión
  pendiente, con mayor tiempo desde registro primero dentro de cada categoría.
  Solo UUID, resumen demostrativo y fechas ya existentes; sin identidad, motivo
  ni signos. No representa episodios activos ni alta clínica, que no existen
  en el esquema. Nunca se infieren niveles III–V.
- Socket.IO namespace `/triage`, engine path `/socket.io`, transporte WebSocket.
  JWT solo en `auth.token`, no URL. Solo MEDICO activo puede conectar, sincronizar
  o recibir avisos; se verifican firma, emisor, audiencia, expiración y rol actual.
  `triage:sync` admite únicamente un objeto vacío y devuelve `{ok:true}`.
  `triage:changed` es exclusivamente de servidor, después de COMMIT: contiene
  `eventId` aleatorio y `criticalDemo` booleano necesario para la alarma I demo.
  No contiene paciente, documento, nombre, signos, motivo o payload cifrado.
- `GET /api/audit/events`: solo AUDITOR. Filtros `from`, `to`, `actorId`, `action`,
  `entityType`; `limit` acotado y `cursor` por ID bigint como texto. Devuelve solo
  ID, fecha, actor UUID, acción, tipo/identificador de entidad. No devuelve emails,
  estados JSON ni IP. Identificadores/acciones no catalogados se redactan.
  No hay rutas para editar/borrar. Se conserva el trigger existente.

Las lecturas de panel/auditoría también se registran antes de devolver datos.
Las escrituras clínicas y sus auditorías existentes siguen siendo transaccionales.
Un fallo de notificación posterior al COMMIT no convierte un registro confirmado
en un error ni provoca una segunda escritura: la recuperación se hace por HTTP.

Los avisos son en vivo y de mejor esfuerzo; no constituyen una alarma clínica
certificada, cola durable ni un sistema de entrega garantizada. La reconexión y
reapertura vuelven a consultar la fuente PostgreSQL sin acumular duplicados.
El sonido de tres segundos requiere activación del usuario por las políticas del
navegador/WebView. La alerta visual funciona aunque el sonido no esté habilitado.

Android debug mantiene la WebView HTTPS y el bloqueo de contenido mixto. Para el
Socket.IO local se prepara un puente nativo debug al único host ya autorizado,
sin permitir WebSockets inseguros globalmente. Release utiliza WSS/HTTPS.

## Detalles de los contratos

`GET /api/triage/panel?page=1&limit=25`: `page` entre 1 y 1000, `limit` entre 1
y 100. Respuesta `{items,totals,page,limit,windowHours:24,demoOnly:true}`.
Cada item contiene `patientId`, `triageId`, `level` I/II/null, `maxWaitMinutes`,
`requiresClinicalReview`, `createdAt`, `elapsedMinutes` y `demoOnly:true`.
`totals` contiene `total`, `levelI`, `levelII`, `pending`. Solo se usa el último
triaje de cada paciente; no hay duplicados por historial. Un registro sin
propuesta I/II utilizable, incluido un valor legado III–V, aparece pendiente
sin proponer nivel o espera. Entre pacientes del mismo nivel se muestra primero
el triaje más antiguo. Un nuevo I precede a los II/pendientes, conservando el
orden por espera respecto de otros I. La consulta y `READ_TRIAGE_PANEL` usan una
transacción REPEATABLE READ.

`GET /api/audit/events`: filtros opcionales `from`, `to` ISO 8601, `actorId` UUID v4,
`action`, `entityType`, `cursor` y `limit` (1–100, predeterminado 25). Intervalo
invertido, filtros desconocidos o cursor fuera de bigint producen 400. Fechas de
la pantalla en hora local se convierten a ISO UTC. `action` acepta el catálogo
de acciones operativas existentes más `READ_TRIAGE_PANEL` y `READ_AUDIT`;
`entityType`: patient/triage/bed/panel/audit. Respuesta
`{items,nextCursor,limit}`; cada item contiene exclusivamente `id` como texto,
`recordedAt`, `actorId`, `action`, `entityType`, `entityId`. El actor se presenta
como UUID, no como nombre/correo. Los UUID son seudónimos operativos, no una
garantía de anonimización irreversible.

El cursor usa `id < cursor`, orden ID descendente, y conserva precisión por encima
de `Number.MAX_SAFE_INTEGER`. `nextCursor:null` indica fin. Los eventos nuevos
se consultan al volver a aplicar filtros; no se hace polling sobre auditoría que
generaría un bucle de `READ_AUDIT`. Las consultas también quedan auditadas antes
de devolver resultados. Un fallo de escritura de la auditoría produce error sin
entregar la lectura. No se ofrecen POST/PATCH/DELETE de auditoría.

Los endpoints devuelven 401 sin JWT válido, 403 con otro rol o cuenta desactivada/
rol cambiado. Las guardas servidor y el rol vigente en `users` deciden el acceso.
Se conservan errores sanitizados y `Cache-Control:no-store`. No se seleccionan
IP, estados JSON ni ciphertext para el informe. Entidades de pacientes/triajes
deben ser UUID, camas deben existir en el catálogo y los identificadores de panel/
auditoría son fijos; valores ajenos se muestran como `REDACTED`.

Socket.IO mantiene JWT en `auth.token` y verifica MEDICO activo en conexión,
`triage:sync` y antes de cada entrega. Desconecta al expirar el token y rechaza
eventos desconocidos, cuerpos extra o intentos cliente de emitir avisos.
Los orígenes explícitos se validan también en `allowRequest`, porque WebSocket
no queda protegido únicamente por CORS HTTP. Clientes nativos sin Origin siguen
necesitando JWT. Se reutiliza `corsOrigins` existente: desarrollo
`http://localhost:8100,https://localhost`; producción solo HTTPS configurado,
sin comodines ni incorporación automática de orígenes locales.

## Reproducir compilación y pruebas

Desde la raíz en PowerShell, usar el Node compatible incluido (el Node global
22.15.0 no cumple el mínimo de este Angular):

```powershell
$env:Path = (Resolve-Path .\apps\mobile\.tools\node-v22.23.5-win-x64).Path + ';' + $env:Path
node -v
docker compose -f compose.yaml -f compose.dev.yaml up -d --build
Invoke-RestMethod http://localhost:3000/api/health
Push-Location apps/api
npm.cmd run test:cov
npm.cmd run build
Pop-Location
Push-Location apps/mobile
npm.cmd run test:unit
npm.cmd run test:e2e
npm.cmd run lint
& "$env:APPDATA\npm\ionic.cmd" build
npx.cmd cap sync android
Pop-Location
```

Para generar el APK local debug, desde `apps/mobile` con JDK 21 y Android SDK
configurados ejecutar `./android-debug.cmd`. Este helper compila con el entorno
`android-debug`, sincroniza y construye `android/app/build/outputs/apk/debug/app-debug.apk`.
Instalar con `adb install -r android/app/build/outputs/apk/debug/app-debug.apk`.
Después de un build producción, volver a usar el helper para debug: `cap sync`
copia exactamente el último `www` compilado. El APK debug ya verificado conserva
su bundle local; el último `www`/sync del cierre quedó en producción para release.

Ejecutar solo pruebas instrumentales de la aplicación:
`android/gradlew.bat -p android :app:connectedDebugAndroidTest`.
Con el APK debug instalado y el emulador abierto,
`node e2e/android-panel-audit.cjs` verifica ambos flujos con datos completamente
aislados; interrumpe brevemente la API Docker y la restaura al finalizar.

## Prueba manual contra Docker con datos ficticios

1. Mantener el Compose de desarrollo activo. Abrir `apps/mobile/serve.cmd` y
   `http://localhost:8100`. En el emulador abrir el APK debug actualizado.
   Usar únicamente cuentas ficticias existentes; no hay contraseñas en código
   ni se deben cambiar las claves de pacientes.
2. Entrar como MEDICO y abrir **Panel médico**. Esperar **En vivo** y pulsar
   **Habilitar sonido de aviso** si se desea comprobar el audio y volumen.
3. En otra sesión del navegador, entrar como ENFERMERO y registrar un documento
   `DEMO-...` único, nombre/motivo ficticios, SpO₂ 84, Glasgow 15 y EVA 1. Confirmar.
   El panel debe recibir aviso, mostrar el resumen I y actualizar sus totales.
   Verificar una alarma de 3 segundos con sonido previamente habilitado.
4. Registrar otro caso con SpO₂ 98, Glasgow 15, EVA 8: II demostrativo. Con EVA 1
   y las dos casillas clínicas desmarcadas: revisión pendiente, sin III–V.
   Confirmar orden I/II/pendiente y solo un registro por paciente.
5. Interrumpir y restaurar la red; volver del segundo plano o salir del panel y
   abrirlo de nuevo. Debe recuperar la consulta vigente sin duplicados. Mientras
   no haya conexión en vivo, usar el estado visible y **Actualizar panel**.
6. Cerrar sesión y entrar como AUDITOR. Abrir **Auditoría**, filtrar por acción,
   entidad, intervalo o UUID de actor; aplicar, avanzar/volver y limpiar. Ver
   fecha, actor, acción y entidad, sin identidad, signos, IP o estados JSON.
   Un UUID ficticio inexistente debe mostrar vacío. No hay edición/borrado.
7. Como SERVICIOS, comprobar que solo tiene sus accesos permitidos, sin panel,
   pacientes o auditoría. Las llamadas directas con su JWT a las dos rutas nuevas
   deben responder 403; la conexión `/triage` debe ser rechazada.
8. Cerrar sesión y recargar. Debe exigir ingreso. No deben aparecer JWT, pacientes
   o resultados en localStorage/sessionStorage. Los registros de esta prueba
   manual sí son persistencias ficticias normales; no eliminarlos para limpiar.

## Límites pendientes

- Sin protocolo III–V, decisiones clínicas adicionales, episodios activos,
  señal de “atendido”, reclasificación por especialista/motivo ni alta clínica.
  El escenario legado HU-08 III→II no se declara terminado.
- Ventana de 24 horas y último triaje son una simplificación académica documentada,
  no un censo de urgencias clínicamente validado.
- Socket.IO de una instancia, sin outbox/Redis ni entrega durable. Un aviso perdido
  se recupera al reconectar/reabrir/actualizar. El censo de camas sigue teniendo
  actualización HTTP y no se declara difusión subsegundo a todos los clientes.
- Alertas mientras el panel está activo, sin notificaciones push en segundo plano.
  Autoplay, volumen y accesibilidad auditiva requieren evaluación humana.
- Auditoría de solo lectura y seudonimizada; trigger protege operaciones normales,
  no impide que un administrador PostgreSQL altere/deshabilite controles. Roles DB
  separados, retención, exportación y almacenamiento inmutable fuerte pendientes.
- Release compilado, sin distribución: `environment.prod.ts` mantiene URL nativa
  vacía que falla de forma cerrada hasta configurar HTTPS real, proxy WSS en
  `/socket.io` y orígenes explícitos. No se habilitó HTTP release.
- La instalación Docker informó cero vulnerabilidades en dependencias runtime;
  el conjunto con herramientas de desarrollo informó 11 (8 bajas, 3 moderadas).
  No se hizo actualización forzada ni se afirma SAST/SCA/DAST integral aprobado.
  Aceptación PO, firma, dispositivo físico y DoD global pendientes.

Se detiene el trabajo en el alcance HU-02/HU-08 solicitado.
