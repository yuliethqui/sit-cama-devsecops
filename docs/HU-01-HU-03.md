# HU-01 y HU-03: persistencia y búsqueda

Implementación académica para datos sintéticos. `classifyTriage` conserva sus reglas de demostración I/II. Los casos no determinados se guardan con `level=null`, `maxWaitMinutes=null` y `requiresClinicalReview=true`. Ninguna propuesta del motor sustituye una valoración clínica; todas las respuestas de triaje incluyen `demoOnly=true`.

## Arquitectura y esquema verificados

Se verificaron `apps/api/db/001_initial.sql` y las columnas/restricciones del PostgreSQL activo antes de implementar. Se reutilizan, sin migraciones ni cambios de esquema:

- `patients`: UUID, `document_hmac` único, `identity_ciphertext` bytea, `provisional`, fecha.
- `triage_records`: paciente, nivel y espera anulables, `clinical_payload_ciphertext` bytea, revisión clínica, autor y fecha.
- `audit_events`: actor, entidad, acción, estados JSON, IP y fecha; conserva el trigger de solo anexado.

El nuevo módulo `patients` usa `DatabaseService` y las guardas JWT/RBAC existentes. `POST /patients` confirma paciente, triaje inicial y dos eventos en una transacción. Los triajes posteriores se anexan con bloqueo de la fila del paciente; no reemplazan registros. La restricción única de HMAC resuelve registros concurrentes del mismo documento con 201/409.

No se modificó `001_initial.sql`, ningún registro existente ni las 38 camas. El esquema no representa episodios de atención, egreso o comienzo real de espera: `triageStatus` describe únicamente la disponibilidad/revisión del triaje y `elapsedMinutes` mide minutos desde su último registro. No representa el estado clínico actual ni una promesa de atención.

## Protección de datos

Identidad (`document`, `fullName`) y motivo/signos se cifran con AES-256-GCM. El sobre binario v1 contiene versión, IV aleatorio de 12 bytes, etiqueta de 16 bytes y ciphertext. La autenticación adicional vincula cada ciphertext a su propósito y UUID; intercambiarlo entre registros o alterarlo impide descifrarlo.

La búsqueda usa HMAC-SHA-256 con clave independiente. Registro y búsqueda recortan espacios exteriores y convierten a mayúsculas; conservan ceros iniciales, puntos y guiones. Los documentos aceptan 3–40 caracteres ASCII alfanuméricos, punto o guion, empezando con alfanumérico. No hay búsquedas parciales, listados generales ni documentos en URLs. Para este MVP el documento constituye una clave única global; aún no se distingue tipo de documento ni se registran pacientes sin identificación.

`REGISTER_PATIENT`, `RECORD_TRIAGE`, `SEARCH_PATIENT` y `READ_TRIAGE` registran UUID, actor e IP, con metadatos mínimos; omiten nombres, documentos, HMAC, motivo, signos y clasificación. Se auditan también las búsquedas exactas sin coincidencia. La lectura solo entrega datos después de confirmar su evento de acceso. Una falla de auditoría produce 500 y revierte la operación. Las denegaciones de JWT/rol ocurren antes del acceso a datos.

La configuración HTTP compartida aplica `Cache-Control: no-store`, validación estricta y errores genéricos, incluidos errores del parser JSON. No se registran excepciones SQL, cuerpos, tokens ni datos descifrados. Mantener esa política si se incorporan proxies, APM o logs de solicitudes. La verificación JWT exige HS256, emisor y audiencia de SIT-CAMA.

Las dos claves se proporcionan mediante variables de entorno. Si faltan, son iguales o tienen formato inválido, las operaciones que requieren criptografía responden 503; health, login, camas y preview siguen disponibles. Conservar estas claves de forma segura: cambiarlas sin una migración de recifrado/reindexación hace inaccesibles los datos o la búsqueda existentes. No hay rotación de claves implementada en este incremento.

## Preparar Docker desde PowerShell

No volver a copiar `.env.example` sobre un `.env` existente. Agregar solo los dos campos nuevos. Desde la raíz, generar **dos** claves independientes (compatible con Windows PowerShell 5.1 y PowerShell 7):

```powershell
function New-PatientKey {
    $keyBytes = New-Object byte[] 32
    $generator = [System.Security.Cryptography.RandomNumberGenerator]::Create()
    try { $generator.GetBytes($keyBytes) } finally { $generator.Dispose() }
    [Convert]::ToBase64String($keyBytes)
}
# Solo la primera vez, si estos campos aún NO existen en .env:
Add-Content -Path .env -Value "`nPATIENT_DATA_KEY=$(New-PatientKey)"
Add-Content -Path .env -Value "PATIENT_HMAC_KEY=$(New-PatientKey)"
docker compose up --build -d api
Invoke-RestMethod http://127.0.0.1:3000/api/health
```

No regenerar claves que ya protejan registros. No se necesita ejecutar SQL ni recrear el volumen. No usar `docker compose down -v`. `.env` y sus secretos nunca se publican. El servicio API recibe las nuevas variables mediante `compose.yaml`.

## Contrato REST y permisos

Todas las rutas llevan el prefijo `/api` y requieren `Authorization: Bearer <JWT>`.

| Método y ruta | Roles | Resultado |
| --- | --- | --- |
| `POST /patients` | ENFERMERO, MEDICO | 201: paciente y resumen del triaje inicial |
| `POST /patients/:patientId/triage` | ENFERMERO, MEDICO | 201: nuevo triaje y resumen; conserva historial |
| `POST /patients/search` | ADMISIONES, ENFERMERO, MEDICO | 200: UUID, provisional, fecha, estado del triaje y último resumen |
| `GET /patients/:patientId/triage/latest` | ENFERMERO, MEDICO | 200: último resumen y motivo/signos descifrados |

ADMISIONES no recibe identidad ni motivo/signos. SERVICIOS, COORDINADOR y AUDITOR reciben 403 en todas estas rutas. El acceso a auditoría y la asignación de camas pertenecen a otras HU.

Errores: 400 por DTO/UUID inválido o campos adicionales; 401 por JWT ausente, inválido o expirado; 403 por rol; 404 por búsqueda exacta sin coincidencia, paciente inexistente al anexar o ausencia de triaje al leer; 409 por documento duplicado; 503 por configuración criptográfica no disponible; 500 por fallo interno. Los cuerpos no reproducen datos de entrada ni detalles de PostgreSQL.

### Autenticación

Usar las cuentas sintéticas creadas con `npm.cmd run db:seed-user` como se explica en README-MVP.md. Cada ejemplo usa JSON UTF-8 explícito para conservar tildes en Windows PowerShell.

```powershell
$base = 'http://127.0.0.1:3000/api'
function ConvertTo-JsonUtf8($value) {
    return ,([System.Text.Encoding]::UTF8.GetBytes(($value | ConvertTo-Json -Depth 6)))
}
$password = [System.Net.NetworkCredential]::new('', (Read-Host 'Contraseña de ENFERMERO o MEDICO' -AsSecureString)).Password
$login = @{ email='enfermero@demo.test'; password=$password }
$session = Invoke-RestMethod "$base/auth/login" -Method Post -ContentType 'application/json; charset=utf-8' -Body (ConvertTo-JsonUtf8 $login)
$headers = @{ Authorization="Bearer $($session.access_token)" }
Remove-Variable password, login
```

### 1. Registrar paciente y triaje inicial

```powershell
$document = 'DEMO-' + [Guid]::NewGuid().ToString('N')
$triage = @{
    chiefComplaint='Motivo sintético de demostración'
    spo2=84; glasgow=15; eva=2
    paroInminente=$false; dolorToracicoTipico=$false
}
$registration = @{ document=$document; fullName='Persona Sintética'; triage=$triage }
$saved = Invoke-RestMethod "$base/patients" -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body (ConvertTo-JsonUtf8 $registration)
$patientId = $saved.patientId
$saved
```

Esperar 201 con `triage.level=I`, `maxWaitMinutes=0`, `demoOnly=true` y UUID. Repetir el mismo registro debe producir 409 sin crear un segundo paciente ni triaje. Para demostrar II, usar otro documento con SpO2 98 y EVA 8. No se envía `level`: la API rechaza campos extra.

### 2. Anexar triaje pendiente de revisión

```powershell
$triage.spo2 = 98
$triage.eva = 1
$newTriage = Invoke-RestMethod "$base/patients/$patientId/triage" -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body (ConvertTo-JsonUtf8 $triage)
$newTriage
```

Esperar 201 con `level=null`, `maxWaitMinutes=null`, `requiresClinicalReview=true`. El registro I original permanece en el historial. No se implementan reclasificación manual ni reglas para III–V.

### 3. Buscar documento exacto (también para ADMISIONES)

```powershell
$found = Invoke-RestMethod "$base/patients/search" -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' -Body (ConvertTo-JsonUtf8 @{ document=$document })
$found
```

Esperar 200 con `triageStatus=PENDING_CLINICAL_REVIEW`, último triaje y `elapsedMinutes`. No retorna nombre, documento, motivo ni signos. Un documento válido inexistente devuelve 404. El índice único existente de HMAC resuelve la coincidencia exacta; falta acordar carga y medir el criterio de menos de 500 ms bajo esa carga.

### 4. Consultar último triaje clínico

```powershell
Invoke-RestMethod "$base/patients/$patientId/triage/latest" -Headers $headers
```

Esperar 200 con `clinical` (motivo/signos) y el último resumen. Con un JWT de ADMISIONES devuelve 403. Para probar la separación de roles, iniciar sesión de nuevo con las cuentas de cada rol y reemplazar `$headers`; con SERVICIOS la búsqueda también debe devolver 403 y el censo `/beds` debe seguir accesible.

## Pruebas y compilación

```powershell
# Desde la raíz, asegurar que PostgreSQL está activo, conservando su volumen:
docker compose up -d db
Set-Location apps/api
npm.cmd run test:cov
npm.cmd run build
```

Se usa `npm.cmd` para evitar la restricción de ejecución de `npm.ps1` en Windows. No se agregaron dependencias.

La integración usa HTTP real contra NestJS y PostgreSQL 17. Por defecto toma únicamente credenciales `POSTGRES_*` del `.env` de la raíz y conecta a `127.0.0.1:5432`. Se pueden sobrescribir con `TEST_PGHOST`, `TEST_PGPORT`, `TEST_PGDATABASE`, `TEST_PGUSER`, `TEST_PGPASSWORD`. La cuenta requiere permiso para crear un esquema. Las claves/JWT y usuarios de pruebas son efímeros y sintéticos.

Cada ejecución crea un esquema aleatorio `sitcama_test_<UUID>`, sin `public` en su `search_path`. Carga allí el esquema original y las 38 camas. Solo elimina ese esquema creado por la propia ejecución. Compara conteos y huellas de las tablas públicas antes/después para detectar modificaciones accidentales. No usa TRUNCATE, borra pacientes existentes ni recrea volúmenes. Si PostgreSQL no está disponible, la integración falla explícitamente; no se omite en silencio.

Se cubren cifrado/HMAC, autenticación, permisos de los seis roles, validación anidada, registro I/II/pendiente, duplicados concurrentes, historial, búsqueda/espera, auditoría transaccional, rollback al fallar auditoría, ciphertext alterado y regresión de endpoints anteriores. La cobertura incluye todo `src` salvo `main.ts`, que solo inicia el proceso; se exige al menos 80 % en ramas, funciones, líneas y sentencias. El workflow local de CI ahora configura un PostgreSQL efímero para estas mismas pruebas; no se ha ejecutado ni publicado en GitHub.
